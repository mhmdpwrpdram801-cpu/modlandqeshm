## 2026.08.9 → 2026.08.10 (فرضِ نانوشته در خودِ بررسی)

**سطح:** اجباری
**قاعده‌ها:** `TEST-11`
**علت:** سه بار در یک روز، بازرس روی کدِ کاملاً درست قرمز داد. هر سه بار بررسی
یک عادتِ کدِ خودمان را قاعده‌ی سکو فرض کرده بود.

### چه کسانی درگیرند

هر مخزنی که بررسیِ ایستا یا لینتِ **دست‌نویس** دارد — الگوی regex روی کد، امضای
«چیزی عوض شد؟»، شمارنده‌ی تگ، هر چیزی که کد را متن‌وار می‌خواند. کتابخانه‌های
آماده (ESLint، Ruff) درگیر نیستند.

فهرستِ نامزدها:

```bash
rg -n "re\.(findall|search|sub)\(.*(function|getElementById|import|class=)" --type py
rg -n "innerHTML\.length|outerHTML\.length" -g '!node_modules'
```

### چطور مهاجرت کن

۱. **هر بررسیِ دست‌نویس را بردار و بپرس: این الگو کدام قاعده را می‌سنجد؟**
   اگر جواب «قاعده‌ی جاواسکریپت/HTML/HTTP» نبود و «چون کدِ ما همیشه این‌طور
   نوشته شده» بود، فرضِ نانوشته پیدا شد.

۲. **نشانه‌ی قطعی:** اگر برای ساکت کردنِ یک قرمزی مجبور شده‌ای **کد** را به شکلِ
   دلخواهِ بررسی دربیاوری (پیشوند به `-` ختم شود، تابع حتماً سرِ خط تعریف شود،
   شناسه حتماً ثابت باشد)، فرض غلط است نه کد.

۳. **دو راه، هر دو مجاز:** یا الگو را محدود کن به همان چیزی که واقعاً اثبات‌پذیر
   است (مثلاً فقط فراخوانی‌ای که شناسه تمامش در همان رشته است)، یا بررسی را
   بردار (`CORE-04`). چیزی که نمی‌شود اثباتش کرد، نباید قرمز بدهد.

۴. **بعدش لبه‌ی مقابل را هم بسنج.** بررسیِ اصلاح‌شده را روی یک نمونه‌ی **عمداً
   معیوب** بزن. اگر باز هم سبز داد، در جهتِ اصلاح زیاده‌روی کرده‌ای و حالا یک
   سبزِ توخالی داری (`CORE-12`) — که ساکت‌تر است و برای همین بدتر.

۵. **هر اصلاح یک نمونه‌ی جفتی بگیرد:** یکی معیوب که باید گرفته شود، یکی سالم که
   نباید قرمز بدهد. نمونه‌ی سالم را **قبل** از اصلاح هم بزن؛ اگر آن‌جا قرمز نشد،
   اصلاً چیزی را اثبات نکرده‌ای (`CORE-03`).

### چطور وارسی کن

```bash
python3 guidelines/self-check.py
python3 guidelines/run-gates.py
```

و برای خودِ بررسی‌های اصلاح‌شده، همان نمونه‌های جفتیِ گامِ ۵ روی نسخه‌ی قبل و بعد.

### خطر و راهِ برگشت

محدود کردنِ الگو می‌تواند پوششش را کم کند — بررسی‌ای که پیشتر ۱۰ حالت را
می‌دید حالا ۸ تا را می‌بیند. این معامله را **آگاهانه** بکن و در کامنتِ همان
بررسی بنویس چه چیزی دیگر سنجیده نمی‌شود. هر گام یک کامیتِ جدا است، پس برگشتش
`git revert` است.

**علت:** قاعده‌ی تازه‌ای اضافه شد که می‌گوید پارسرِ نرمِ ورودیِ انسانی حق ندارد روی

### چه کسانی درگیرند

پارسرهای نرمِ خودت را پیدا کن (تابعی که ورودیِ آدم را «می‌فهمد»: جداکننده‌ی هزار
می‌اندازد، رقمِ فارسی را برمی‌گرداند، فاصله را می‌بُرد)، بعد ببین کدام‌شان روی چیزی

```bash
rg -n 'function (parseNum|parseAmount|toNumber|parseMoney|normalize\w*)' --glob '!node_modules'
rg -n '(parseNum|parseAmount|toNumber|parseMoney)\(' --glob '!node_modules' \
  | rg -v '\.value|getElementById|querySelector|\binput\b'
```

خروجیِ خالیِ فرمانِ دوم یعنی پارسرِ نرم فقط روی فیلدهای فرم می‌نشیند — **درگیر
نیستی، مُهر را جلو ببر.** در همین مخزن هر ۱۶ فراخوانیِ `parseNum` در
`panel/index.html` روی `.value`ِ یک فیلد است (وارسی شد)، پس مهاجرت بی‌اثر است.

همین را برای مرزهای دیگر هم بپرس: پاسخِ سرویس، فایلِ واردشده، ردیفِ
`localStorage`، پارامترِ آدرس. هر جا `parseInt`/`parseFloat`/`Number()` روی داده‌ی
بیرونی بی‌محافظ نشسته، همان‌جاست.

### چطور مهاجرت کن

1. **برای هر مرز یک پارسرِ جدا بنویس.** پارسرِ انسانی دست‌نخورده می‌ماند؛ مرزِ
   ماشین پارسرِ سخت‌گیرِ خودش را می‌گیرد:
   ```js
   function amountOf(v){
     if(typeof v==='number') return Number.isSafeInteger(v)?v:NaN;
     if(typeof v!=='string') return NaN;
     var s=toAscii(v).replace(/\s/g,'').replace(/[٬,]/g,'');   // «.» اینجا ممیز است، رد شود
     return /^\d{1,15}$/.test(s)?parseInt(s,10):NaN;
   }
   ```
2. **ردشده‌ها را بشمار و نشان بده.** «۲ ردیف اضافه شد، ۳ ناسالم» شاهد است؛
   «۵ ردیف اضافه شد» دروغِ خاموش.
3. **پیش از اصلاح، بررسیِ رگرسیون بنویس** که با یک فایل/پاسخِ حاوی مقدارِ مرزی
   قرمز شود (CORE-03).

### چطور وارسی کن

یک فایل/پاسخِ نمونه با مقدارِ اعشاری بساز و از **همان مسیری که کاربر می‌رود** واردش
کن (کلیکِ واقعی روی input، نه صدا زدنِ تابع — TEST-02). قبل از اصلاح باید مقدارِ
ضرب‌شده ذخیره شود و بعدش رد شود:

```bash
python3 <بررسیِ رگرسیونِ خودت>    # قبل: کدِ خروجی ۱ · بعد: ۰
python3 guidelines/self-check.py
```

### خطر و راهِ برگشت
پارسرِ سخت‌گیر ممکن است داده‌ی قدیمیِ سهل‌گیرانه‌پذیرفته‌شده را رد کند — پس **اول
بشمار چند ردیف رد می‌شوند** و اگر عدد غیرصفر بود، قبل از سخت کردن یک مهاجرتِ داده
