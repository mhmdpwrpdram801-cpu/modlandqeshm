# سنجشِ انطباق

دامنه: `$1` (اگر خالی است، کلِ مخزن)

**این دستور هیچ فایلی را عوض نمی‌کند.** خروجی‌اش یک گزارش است تا کاربر تصمیم بگیرد.

## کارها

1. `guidelines/FULLSTACK.md`، `guidelines/lock.json` را بخوان.
2. `python3 guidelines/self-check.py` را اجرا کن. اگر قرمز بود، **همان اول بگو** —
   دستورالعملی که با خودش نمی‌خواند، مبنای سنجش نیست.
3. `waivers` را بخوان. هر چیزی که استثنا دارد **اصلاً گزارش نمی‌شود** (MIG-05).
   استثناها را با «اختلاف» قاطی نکن.
4. کدِ داخلِ دامنه را بخوان و با قاعده‌ها بسنج. تمرکز بر این ترتیب:
   امنیت (§۸) → داده (§۶) → درستی و تست (§۱۰) → مرزِ API (§۷) → رابطِ کاربری (§۹) → بقیه.
5. **انتخابِ فناوری را گزارش نکن** مگر کاربر صریح خواسته باشد (PREC-02، MIG-04).
   «این پروژه React ندارد» اختلاف نیست.

## قالبِ گزارش

برای هر اختلاف، دقیقاً این چهار چیز:

```
[شناسه‌ی قاعده] مسیرِ فایل:شماره‌ی خط
چه چیزی هست:  ...
چرا مهم است:  یک سناریوی مشخصِ خرابی — نه «بهتر است»
هزینه‌ی اصلاح: کوچک | متوسط | بزرگ
```

گروه‌بندی در سه دسته:

- **باید درست شود** — امنیت، از دست رفتنِ داده، محاسبه‌ی غلطِ پول، دسترسیِ شکسته
- **بهتر است درست شود** — تله‌ای که دیر یا زود می‌گیرد
- **بماند برای بعد** — بدهیِ فنیِ آگاهانه

## قاعده‌ها

- **شاهد بده، حدس نه.** هر اختلاف باید مسیر و خطِ واقعی داشته باشد. اگر ندیده‌ای، ننویس.
- **سناریوی خرابی بنویس، نه سلیقه.** «این با قاعده نمی‌خواند» گزارشِ بی‌ارزش است؛
  «اگر نامِ کالا بلند باشد، عددِ قیمت بریده می‌شود» گزارشِ باارزش.
- اگر هیچ اختلافی نبود، همین را بگو. فهرست را با موردِ بی‌اهمیت پر نکن.
- در پایان بپرس کدام دسته را اصلاح کند — خودت شروع نکن.
